# CUCPU 固定延迟执行与四槽提交方案

本文记录第一版流水执行方案：单发射、顺序发射、独立执行单元、允许乱序完成、按序提交，并通过 forwarding（结果转发）解决操作数依赖。

这是微架构草案，尚未实现。指令编码和零寄存器等架构约定见 [ISA.md](ISA.md)。

## 1. 目标与适用范围

- 每周期最多发射一条指令，但允许多条指令同时在不同执行单元中运行。
- 顺序发射，不让后面的指令越过正在等待操作数的指令。
- 暂不做多发射、寄存器重命名和乱序挑选指令。
- 简单 ALU、乘法和乘加可以具有不同延迟，但每种已支持操作的延迟必须固定，且最大为 4 周期。
- 已接收的指令必须按约定时间产生结果，执行流水线内部不允许延长延迟的停顿。
- 每周期最多提交一条指令，结果缓冲和寄存器写入不得使提交额外停顿。
- 使用四个独立寄存器槽位保存指令元数据及结果，支持同周期多个执行单元完成。
- 暂不把 `IDIV`、`IREM` 纳入该方案。存在未知延迟的访存、异常和分支恢复也需要单独设计。

固定延迟表描述硬件的时间契约，不会自动生成相应流水级。`op_latency` 与执行单元的实际实现必须一致。延迟为 0 的未支持操作不能当作正常指令发射。

## 2. 数据流

```text
译码 → 顺序发射与依赖检查 → ALU / MUL / 其他固定延迟单元
                ↑                            ↓
       寄存器组、槽位结果、完成旁路       按槽位编号返回结果
                ↑                            ↓
                └──── 四槽结果存储 ←──────────┘
                           ↓
                       按序提交
                           ↓
                       寄存器组
```

发射阶段先选择并锁存实际操作数，再发送给执行单元。发射请求中的操作数是数据值，而不是留待执行单元以后读取的寄存器编号。

执行单元不必使用通用 `resp_valid/resp_ready` 握手。每个单元保留自己的完成信号、槽位编号和结果输出；完成端必须能按时接收结果。执行单元是否能接收新请求仍需要检查，例如非流水化乘法单元可能尚未空闲。

## 3. 周期和延迟的定义

用时钟边沿编号表示周期。指令在边沿 `a` 被接收，延迟为 `L`，表示其结果最迟在边沿 `a + L` **可以被提交或转发逻辑采样**。

因此，在边沿 `a + L` 才写入某个输出寄存器、边沿之后才变得可见的结果，不能在同一边沿从该寄存器读取并提交。必要时应从该寄存器前的完成数据直接旁路，或重新计算包含最终写回级的延迟。

本方案中的最大 4 周期必须包含结果到提交端的时间。不能只计算算术流水级，然后额外增加一个未计入的缓冲或写回周期。

## 4. 槽位分配

指令在周期 `a` 发射时，分配：

```text
slot = a mod 4 = 发射周期的低 2 bit
```

这里使用的是持续推进的周期计数，不因发射停顿而暂停。没有发射的周期不会分配槽位。

同一槽位的两次分配至少间隔 4 周期。证明旧指令在这之前已经提交，才能保证安全复用；仅证明执行完成还不够。

建议每个槽位保存：

| 字段 | 用途 |
| --- | --- |
| `valid` | 槽位是否有尚未提交的指令 |
| `ready` | 结果是否已存入槽位 |
| `rd` | 目的寄存器编号 |
| `write_rd` | 是否更新目的寄存器；写 `r0` 时不更新寄存器组 |
| `value` | 已完成的运算结果 |
| 顺序信息 | 用于识别最老待提交指令及最新相关生产者 |

顺序信息的具体实现待定，可以使用周期记录、年龄关系或独立控制表。不能直接按槽位编号的数值大小判断新旧，因为编号会回绕。

这些槽位物理上可以是四组寄存器，但逻辑上仍承担在途指令跟踪、结果保存和按序提交的职责。

## 5. 四槽容量证明

只考虑正常执行、没有取消或异常的已发射指令，并满足第 1 节的假设。

对第 `i` 条指令定义：

- `a_i`：发射周期。
- `L_i`：执行延迟，`1 <= L_i <= 4`。
- `c_i`：提交周期。

单发射保证：

```text
a_i >= a_(i-1) + 1
```

若采用队列头就绪即提交的策略，按序提交且每周期一条给出：

```text
c_i = max(a_i + L_i, c_(i-1) + 1)
```

第一条指令满足 `c_0 = a_0 + L_0 <= a_0 + 4`。

假设上一条满足 `c_(i-1) <= a_(i-1) + 4`，则：

```text
a_i + L_i <= a_i + 4

c_(i-1) + 1
    <= a_(i-1) + 5
    <= a_i + 4
```

故 `c_i <= a_i + 4`。归纳可知，每条指令都能在发射后最多 4 周期提交，完成结果不会无限积压。

因此，周期 `a` 使用的槽位到周期 `a + 4` 必须已经释放，或在该周期提交并立即复用。边沿更新完成后最多有四条尚未提交的指令。

这个证明允许延迟为 1、2、3、4 的指令任意混合，也允许发射出现空泡；并不要求所有操作都执行恰好 4 周期。

### 可选的更简单提交策略

也可以将每条指令的提交时间统一设为 `a_i + 4`。即使结果提前产生，也只用于转发，到固定周期才提交。

由于每周期最多发射一条，固定偏移后的提交周期不会冲突；所有结果又保证在该周期可用。因此它同样满足四槽容量要求。

这种方式可以利用延迟 4 周期的发射有效标记与槽位信息确定提交对象，减少寻找队列头的控制，但会让短延迟指令更晚更新寄存器组。提前完成的结果仍可转发，不必等提交后才使用。

“就绪即按序提交”与“统一第 4 周期提交”都是可行选项，具体选择尚未定稿。

## 6. 完成、提交和复用的同周期规则

一个周期可能同时发生：

1. 多个执行单元完成，写入不同槽位。
2. 最老指令提交，更新寄存器组。
3. 新指令读取操作数并发射。
4. 新指令复用本周期刚提交的槽位。

建议明确以下规则：

- 提交和操作数选择读取旧指令的元数据，以及已有结果或本周期完成结果。
- 同周期完成但尚未存入槽位的结果，通过完成旁路供提交及转发使用。
- 若旧指令提交后槽位被新指令复用，边沿后的槽位状态必须属于新指令：`valid = 1`、`ready = 0`，并更新其元数据。
- 旧指令的完成写入或提交清除不能覆盖新指令的槽位初始化。
- 操作数读取不能误用本周期新分配的指令元数据。
- 复位时所有槽位无效，执行流水级的有效标记也清零。

RTL 应显式组合这些条件和更新优先级，避免依赖多个非阻塞赋值之间未经说明的覆盖关系。

## 7. 同周期多个结果

单发射不代表单完成。例如乘法延迟 3、加法延迟 1 时，周期 0 发射乘法、周期 2 发射加法，会在周期 3 同时完成。

四槽方案吸收这类完成突发，不需要提前预约唯一的完成周期。但硬件必须支持多个单元同时写入不同槽位，不能把四个槽位接到一个只能接收单结果的写入口。

第一版可用寄存器实现各槽位的数据和状态，为每个槽位选择对应完成输入。还应检查正常情况下不会有两个完成输入同时指向同一槽位。

## 8. 操作数依赖与 forwarding

根据 [ISA.md](ISA.md) 的 ALU 编码约定，只有未使用的源操作数字段必须为 0，由汇编器保证。立即数位置是有效操作数，其原始源字段保存立即数的高 5 bit，不要求为 0。

issuer 先用 `imm_sel` 将立即数位置的有效 RF 地址置为 0，保留原始源字段用于与低 27 bit 拼接。然后对三个有效 RF 地址统一查询：地址为 0 时返回零且不建立依赖；非零时通过 scoreboard 找到生产者槽位，再检查结果是否可用。不需要另设 `src_used` 标志屏蔽未使用位置，但必须屏蔽立即数位置，避免把其高位当作寄存器编号。查询后，立即数位置使用 `{原始源字段, imm}` 形成的完整 32 bit 值。该规则仅针对目前的 ALU 编码，其他指令类型另行规定。

对每个有效 RF 地址：

| 情况 | 数据来源或行为 |
| --- | --- |
| 源为 `r0` | 常量零 |
| 没有在途指令写该寄存器 | 寄存器组 |
| 最新的相关生产者已完成 | 对应槽位的结果 |
| 最新的相关生产者本周期完成 | 执行单元完成旁路 |
| 最新的相关生产者尚未完成 | 暂停当前指令发射 |

`ready` 和完成信号足以判断结果是否可用；不需要仅靠预计延迟推断数据有效性。

### 多个生产者

若允许两条在途指令写同一个寄存器，消费者必须选择程序顺序中最近的生产者。较老生产者已经完成，不能替代较新但尚未完成的生产者。

第一版建议先禁止 WAW：目的寄存器存在尚未提交的写入时暂停发射。这样每个非零寄存器最多有一个在途生产者，可以简化依赖及转发选择。是否允许多个生产者仍是待定实现选择。

### 操作数锁存与同周期提交

所有源操作数在发射时确定并锁存，后续寄存器组写入不能改变已发射指令的输入，避免 WAR 问题。

同周期提交和读取相同寄存器时，必须读到该旧指令的新结果。可从提交/完成路径转发，不能默认寄存器组天然具有写优先读行为。

写 `r0` 的指令仍按其正常执行和提交规则处理，但不建立 `r0` 的数据依赖，也不将结果转发为 `r0` 的值。

## 9. 超出证明条件的情况

以下变化需要重新设计容量或增加发射限制：

- 支持超过 4 周期或未知延迟的操作，例如除法或某些访存。
- 完成端、提交端被阻塞，或结果必须额外停留一个未计入延迟的写回级。
- 异常、存储副作用等要求阻止队列头继续提交。
- 多发射，或改变提交宽度和顺序规则。

不得因为时间到达就覆盖仍有效的槽位。即使依赖容量证明，RTL 也应检查目标槽位空闲或本周期确实提交释放。

若未来增加分支取消，低 2 bit 槽位编号不能单独防止旧结果误写新指令。需要保证取消后的旧结果不会到达复用槽位，或增加代际标记并校验。复位也要同时清除执行单元中的旧有效信息。

## 10. 实现前检查项

1. 确定实际支持操作及固定延迟，检查全部位于 1～4 周期。
2. 决定采用就绪即按序提交，还是统一第 4 周期提交。
3. 定义槽位状态、顺序信息及执行完成信号。
4. 明确时钟边沿契约和完成到提交、操作数选择的旁路路径。
5. 决定第一版是否禁止 WAW，并按 ALU 源字段为零的编码约定实现依赖查询及立即数替换。
6. 检查同周期多完成、提交与复用的更新优先级。
7. 验证不同延迟混合、发射空泡、RAW 等待、写 `r0` 及编号回绕。
8. 验证所有已接收指令按时产生结果、每条指令只提交一次、槽位不会提前覆盖。

上述四槽结论是带条件的容量保证，不代表当前 RTL 已实现或达到该时序。
