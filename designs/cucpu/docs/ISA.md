# CUCPU 指令集设计草案

本文记录 CUCPU 当前的设计约定和待定事项，用于后续实现译码器、ALU、寄存器组和测试程序。尚未分配的操作码和修饰位不代表已经支持的功能。

固定延迟流水执行、四槽结果存储和转发方案见 [EXECUTION.md](EXECUTION.md)。

## 1. 当前设计约定

- 每条指令固定为 64 bit。
- 指令包含一个 8 bit 的操作码，其中 2 bit 表示指令类型，6 bit 表示该类型内的具体指令 ID。
- 指令类型计划包含计算、访存、控制流；具体类型编码及第 4 类的用途待定。
- 通用寄存器共 32 个，编号为 `r0`～`r31`，寄存器编号占 5 bit。
- `r0` 是零寄存器：读取始终返回 0，写入被静默丢弃，不改变其值。
- ALU 指令采用一个目的寄存器、三个源操作数的格式，最多一个源操作数来自立即数。
- ALU 指令未使用的源操作数字段必须编码为 0，由汇编器保证；立即数操作数不属于未使用的操作数。
- 立即数由选中源字段的 5 bit 与 `imm` 字段的 27 bit 拼接，组成完整的 32 bit。
- **本文下面的详细字段布局只适用于 ALU 指令。** 访存、控制流等指令分别设计自己的后续字段，不要求保留相同的寄存器字段、立即数字段或修饰字段。

指令长度和寄存器数据宽度是两个独立概念。固定 64 bit 指令不意味着寄存器必须为 64 bit。当前 ALU 的 `WIDTH` 默认值为 32，最终的架构数据宽度仍需确定。

## 2. ALU 指令格式

采用 2 bit 的 `imm_sel` 选择立即数替代哪个源操作数，将原来的三个立即数标志压缩为一个选择字段。剩余 7 bit 留给指令的细化描述。

以下是建议的位位置：操作码放在高位，立即数放在低位。字段宽度来自当前方案；具体位位置作为后续编码的草案。

| 位范围 | 位宽 | 字段 | 含义 |
| --- | --- | --- | --- |
| `[63:62]` | 2 | `type` | 指令类型；本格式要求为 ALU 类型 |
| `[61:56]` | 6 | `id` | ALU 指令 ID |
| `[55:49]` | 7 | `modifiers` | 按具体指令解释的修饰字段 |
| `[48:44]` | 5 | `rd` | 目的寄存器编号 |
| `[43:39]` | 5 | `rs1` | 第一个源寄存器编号，或选中该位置时的立即数高 5 bit |
| `[38:34]` | 5 | `rs2` | 第二个源寄存器编号，或选中该位置时的立即数高 5 bit |
| `[33:29]` | 5 | `rs3` | 第三个源寄存器编号，或选中该位置时的立即数高 5 bit |
| `[28:27]` | 2 | `imm_sel` | 立即数替代哪个源操作数 |
| `[26:0]` | 27 | `imm` | 立即数的低 27 bit |

位宽校验：

```text
2 + 6 + 7 + 5 + 5 + 5 + 5 + 2 + 27 = 64
```

这个布局与内存中的字节序无关。取指后得到的 64 bit 指令如何从内存字节组装，需另行规定。

## 3. 源操作数与立即数

建议将 `imm_sel` 编码为：

| `imm_sel` | 第一个操作数 | 第二个操作数 | 第三个操作数 |
| --- | --- | --- | --- |
| `00` | `R[rs1]` | `R[rs2]` | `R[rs3]` |
| `01` | `extend({rs1, imm})` | `R[rs2]` | `R[rs3]` |
| `10` | `R[rs1]` | `extend({rs2, imm})` | `R[rs3]` |
| `11` | `R[rs1]` | `R[rs2]` | `extend({rs3, imm})` |

`R[n]` 表示读取寄存器 `n`，其中 `R[0]` 始终为 0。`{rsN, imm}` 表示拼接：选中源字段提供高 5 bit，`imm` 提供低 27 bit。在当前 32 bit 数据宽度下，`extend` 是恒等转换，不需要额外扩展。

该编码从结构上保证最多一个立即数。每条具体指令仍需规定：

- 实际使用几个源操作数。
- 允许立即数出现在哪些操作数位置。
- 如果将来支持非 32 bit 数据宽度，如何扩展或截断完整的 32 bit 立即数。

例如，普通加法只使用前两个操作数，不因格式提供了 `rs3` 就必须读取第三个寄存器。三源格式为需要三个操作数的指令保留了空间，并不表示第一版必须实现乘加等功能。

源寄存器字段采用以下编码约定：

- 一元操作未使用的 `rs2`、`rs3` 必须为 0。
- 二元操作未使用的 `rs3` 必须为 0。
- `imm_sel` 选择的源位置是有效操作数，该字段保存立即数高位，可以为任意 5 bit 值，不要求为 0。不得选择指令不使用的源位置。
- 其他操作按实际使用的源位置遵循相同规则，不允许在未使用的源寄存器字段中携带其他信息。

汇编器必须生成符合这些要求的编码；违反要求的编码为非法，其具体处理机制待定。issuer 先根据 `imm_sel` 把立即数位置的有效 RF 地址置为 0，保留原始源字段用于拼接立即数，再统一查询依赖。有效 RF 地址为 0 时取零且不查询生产者，非零时查询 scoreboard。最后将选中位置替换为完整立即数。不能直接把原始立即数高位当作寄存器编号查询依赖。

另建议 `imm_sel = 00` 时的 `imm` 填零；这一立即数保留字段规则及其合法性检查尚未定稿。

### 立即数范围

- 若按有符号数解释，完整 32 bit 立即数的范围为 `-2^31`～`2^31 - 1`。
- 若按无符号数解释，范围为 `0`～`2^32 - 1`。
- 当前格式能够直接表示任意 32 bit 常量，不需要为补足立即数位宽另行设计装载序列。
- 例如 `-1` 的位串为 `32'hFFFFFFFF`，选中源字段填 `5'b11111`，`imm` 填 27 bit 全 1。

立即数编码保存完整位串，运算是否按有符号解释由具体指令语义决定。若以后改变数据宽度，需要明确 32 bit 立即数的扩展或截断规则。

## 4. 指令修饰字段

`modifiers` 用于细化基础指令的行为，例如有符号/无符号比较、逻辑/算术右移等。**其含义由指令 ID 决定，不必对所有 ALU 指令统一解释。**

大小比较（ILT、ILE、IGT、IGE）使用 `modifiers[0]`：0 表示两个操作数均按无符号解释，1 表示均按有符号解释。公共常量 `ALU_MOD_SIGNED_BIT` 定义该位号。IEQ、INE 不受符号位影响。比较成立返回 `DW` 位全 1，否则返回全 0；其余修饰位尚未分配。

SHL、SHR 将 rs1 移位，移位量只取 rs2 的低 5 位（DW=32），即按模 32 处理，移位 32 等同于移位 0。SHL 低位补 0，忽略符号修饰位；SHR 使用 `modifiers[0]`：0 为逻辑右移，高位补 0；1 为算术右移，高位补 rs1 的原始符号位。两者均为五层组合逻辑，不增加内部流水寄存器。

IMUL_LO、IMUL_HI 当前仅按无符号计算 rs1 × rs2，分别返回完整 64 bit 乘积的低、高 32 bit。当前乘法忽略 modifiers，有符号乘法尚未实现。乘法完全流水化，每周期可接收一条；总执行延迟为三级（executor 输入寄存器及 imul 内两级寄存器），完成后通过三周期 complete 通道进入提交队列。

以下仅是用途示例，尚未分配实际位号或操作码：

| 操作 | 可能的细化行为 | 说明 |
| --- | --- | --- |
| 比较 | 有符号 / 无符号 | 同一位串按不同数值解释，比较结果可能不同 |
| 右移 | 逻辑 / 算术 | 高位填零或复制符号位 |
| 乘法 | 低半部 / 高半部，高半部的符号解释 | 低半部结果位不受有符号/无符号解释影响，高半部会受影响 |
| 除法、取余 | 有符号 / 无符号 | 结果可能不同，还需规定除零等行为 |
| 加法、减法 | 是否检查或报告溢出，若架构需要 | 只保留低 `WIDTH` 位时，有符号与无符号的结果位相同，但溢出判断不同 |
| 与、或、异或 | 通常不需要符号修饰 | 按位运算本身没有有符号/无符号区别 |

窄数据加载的符号扩展/零扩展属于访存指令的语义，未来可以在访存格式中定义；不要求复用这里的字段位置。

建议未分配的修饰位必须为零，非零时判为非法编码。这样保留后续扩展空间，也有助于发现编码错误。此规则目前是建议，尚未作为架构约定定稿。

## 5. 指令编码与 ALU 接口

8 bit 操作码是架构层的指令编码，不要求直接连接到 `alu.sv` 的 `op` 输入。

建议由译码器生成内部控制信息：

```text
64 bit 指令
    ↓ 译码器
ALU 操作、操作数选择、写回控制，以及其他执行控制
    ↓ 操作数读取与选择
ALU 输入数据和内部 alu_op
    ↓ 运算与写回
目的寄存器
```

不同指令可以映射到同一个内部 ALU 操作。例如，寄存器加法、立即数加法，以及未来访存指令的地址计算，都可能使用 ALU 的加法功能。

ALU 的内部操作码位宽由实际支持的运算数量决定，不必与指令的 8 bit 操作码或 6 bit ID 等宽。当前实现使用 `common.sv` 中 `cucpu_common` 包的 `alu_op_t`，暂定为 6 bit，仍不构成最终架构编码约定。

公共位宽常量也位于该包中，使用 `cucpu_common::DW` 等名字引用，不使用宏或 `include`。编译时必须先读取 `common.sv`，再读取引用它的模块；项目的仿真和综合脚本已按此顺序处理。未来添加 OpenLane 配置时，`VERILOG_FILES` 也应遵循这个顺序。

该包还提供原始指令类型：`instr_t` 包含 `op_group`、`op_code`、`payload`，总宽度为 64 bit。`instr_payload_t` 是 56 bit 的 packed union，其中 `alu` 使用 `alu_payload_t` 结构，`memory`、`control` 暂为原始位串占位，`raw` 用于整体访问 payload。联合体不会检查指令组，使用 ALU 视图前仍需判断 `op_group`。

RTL 工具链已升级到固定版本的 OSS CAD Suite，综合使用 Yosys 的 `read_slang`。包导入、嵌套结构体/联合体及枚举类型转换均已通过仿真和综合检查，不再需要旧版工具的条件导入兼容写法。可以在模块参数和端口前导入包：

```systemverilog
module instr_view
    import cucpu_common::*;
(
    input  instr_t instr,
    output logic [4:0] rs1
);
    assign rs1 = instr.payload.alu.rs1;
endmodule
```

`instr.op_code` 是普通位串。如果 ALU 指令编码与内部枚举编号一致，可以使用 `alu_op_t'(instr.op_code)` 转换；转换不检查操作码是否合法，仍需判断指令组及有效编码。

OpenLane 的物理实现工具保持原版本，流程入口会先通过新版前端转换为普通 Verilog，再交给 OpenLane。详见仓库根目录 README 的工具链说明。

若要求同一拍取得三个任意源寄存器的值，寄存器组需要三个读端口；也可以采用分多拍读取的实现。指令格式不规定 ALU 必须为组合逻辑、寄存输出或多周期实现，这些属于微架构选择。

## 6. 固定长度与其他指令格式

第一版保持全部指令固定为 64 bit，优先降低取指和指令边界处理的复杂度。某些指令暂时用不满全部位是可以接受的。

共同的 8 bit 操作码提供类型和 ID，剩余 56 bit 由各类指令分别解释：

| 指令类型 | 后续字段可能需要描述的内容 | 状态 |
| --- | --- | --- |
| ALU | 修饰信息、目的寄存器、源操作数、立即数 | 本文已给出草案 |
| 访存 | 数据寄存器、基址、偏移、访问宽度、加载扩展方式等 | 待设计 |
| 控制流 | 条件、比较操作数、目标地址或相对偏移等 | 待设计 |
| 第 4 类 | 用途尚未确定 | 待设计 |

若采用按字节寻址的 PC，顺序执行下一条指令通常为 `PC + 8`；PC 的地址单位、对齐要求和跳转规则仍需明确。

固定 64 bit 相较固定 32 bit，在指令条数相同时需要两倍的代码空间和指令读取字节数。未来可以评估较短指令或有限的多长度编码，但目前不引入变长取指规则。

## 7. 下一步需要确定的内容

在实现完整译码前，建议先确定最小指令集，并逐条写清：

1. 指令类型编码和各类型内的指令 ID。
2. 寄存器数据宽度、内存字节序、PC 地址单位及对齐要求。
3. 每条 ALU 指令的运算语义、实际源操作数数量、允许的立即数位置及扩展方式。
4. 修饰字段的有效位、取值及非法组合。
5. 溢出和除零等尚未定义的边界行为。
6. 写回规则：哪些指令写寄存器，写 `r0` 时仍执行哪些其他行为。
7. 非法指令的处理方式，以及未使用字段、保留位的检查规则。
8. 任意宽度常量的装载方式，以及访存、控制流各自的编码格式。

先确定指令语义，再分配具体 ID 和修饰位，最后据此实现译码器和 ALU 内部操作码。
